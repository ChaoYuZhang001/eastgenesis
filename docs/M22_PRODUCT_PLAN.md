# M22 产品路线：一个任务工作台，多模型可靠执行

日期：2026-10-05
适用项目：EastGenesis Desktop
当前阶段：Alpha / 内部 QA

## 1. 产品决定

EastGenesis 不再把 Chat、Work、Codex 做成三个需要用户先选择的产品模式。它们是同一个任务工作台里的三种能力面：

- **Chat**：对话、问答、解释和推理。
- **Work**：研究、本地文件、文档、表格、演示和可交付成果。
- **Codex**：代码仓库、终端、测试、构建和开发操作。

用户只提交一个目标。系统根据文字、附件、项目上下文、工作目录和当前步骤需要的工具，自动选择能力面和模型。一个目标可以在不同步骤中依次使用 Work、Codex、Chat，不要求用户中途切换模式。

产品定位采用两层策略：

1. **能力基线对齐 ChatGPT Desktop**：对话、文件、项目、记忆、自定义指令、联网、语音、快捷唤起、任务组织和桌面集成，按用户价值逐项补齐。
2. **核心差异化建立在执行控制面**：模型中立、路由透明、失败可恢复、智能路由。复制的是成熟交互和能力，不复制供应商绑定、隐藏路由和不可解释的失败行为。

一句话定位：

> 一个把对话、文件和代码统一到同一条可恢复任务链上的桌面 AI 工作台，模型由任务决定，路由对用户可解释，失败可以继续。

## 2. 当前判断

当前代码已经具备继续推进所需的主要骨架：

- `WorkSurface` 已把 Chat、Work、Codex 表达为能力面，而不是产品模式。
- 路由器已经按能力、质量、成本、延迟和 Provider 健康度评分，并生成跨 Provider 的候选链。
- 回答区已经可以显示路由、降级、部分输出和恢复状态。
- 目标、项目、会话和执行步骤已经有持久化模型。
- 工具调用账本、租约、恢复探测和 QA 崩溃注入已经存在。
- 流式传输、取消、截断响应、Provider 失败策略和本地 HTTP 回环测试已经有自动化证据。
- 原生目录选择器、Mac QA 包、跨平台 CI 草案和发布闸门已经接入。
- `pnpm desktop:gate -- --json` 已把本地协议夹具、Provider 恢复、前端回归和证据边界收敛为单份脱敏结果；加入 `--include-bundle --include-package` 才会把当前平台的桌面产物烟测纳入必需阶段。

因此现在不需要再做一次架构重写，也不应先扩展更多表面功能。项目当前的主要缺口是证据和真实边界：真实 Tauri WebView、真实 Provider 失败、Windows/Linux 安装包、签名与 notarization，以及安全和性能基线仍未完成。发布状态必须继续写成 Alpha / 内部 QA，不能称为 ChatGPT Desktop 级别的公开产品。

## 3. M22 的目标

M22 只解决一个问题：

> 当用户提交一个跨 Chat、Work、Codex 的真实目标时，系统能否在桌面端透明地选择模型，遇到失败保留进度并安全恢复，且用户能理解发生了什么？

### M22 完成定义

一个真实目标必须同时满足：

1. 用户只提交一次目标，不需要先选择 Chat、Work 或 Codex。
2. 时间线能显示当前步骤的能力面、Provider、模型和选择理由。
3. 主模型失败时，系统按照策略重试或换 Provider，并把尝试顺序显示出来。
4. 流式回答中断时保留部分正文，不把两个模型的正文静默拼接。
5. 工具副作用未知时停在 `needs_user`，不自动重放有风险的写操作。
6. 进程在账本关键窗口退出后，重启能够从安全边界继续，且不会重复已经落地的副作用。
7. 同一条路径在 Mac QA 包中有可复盘证据；Windows/Linux 至少有原生 CI 构建和明确的待验证项。

## 4. 优先级顺序

### P0：完成真实桌面闭环

先按 [M21_DESKTOP_RELEASE_GATE.md](./M21_DESKTOP_RELEASE_GATE.md) 完成 Mac QA 包的六条黄金路径：

- staged 流式响应；
- 首 token 延迟；
- 截断和部分输出；
- headers 到达前后的取消；
- 两个账本崩溃窗口的恢复；
- 原生目录选择器和白名单重启错误。

每条路径必须保留任务 ID、路由事件、Provider/模型、时间戳、最终状态、账本状态和应用日志。人工点击没有这些字段，只能算“看过界面”，不能算验收。

### P1：真实 Provider 中立性

至少接入并实测三类 Provider：

1. 一个 OpenAI-compatible 云端 Provider；
2. 一个不同协议或不同供应商的云端 Provider；
3. 一个本地或局域网 Provider，例如 Ollama / LM Studio 类适配器。

真实测试只使用临时测试账号或本地代理，凭据通过钥匙串或环境变量注入，不写入日志、截图、报告和提交。需要覆盖 401/403、404、429、5xx、网络断开、超时、取消和工具副作用未知八类场景。

这一步的交付不是“多接几个模型”，而是证明以下契约对所有适配器成立：

```text
ProviderAdapter
  request / stream
  normalized error
  usage and cost (if available)
  cancellation
  partial output
  retry safety
```

任何适配器不能表达取消、部分输出或错误类别，就不能进入自动路由候选链，只能作为手动锁定的实验适配器。

### P1：路由透明度 v1

用户看到的路由信息只保留四件事：

- 这一步需要什么能力；
- 实际用了哪个 Provider / 模型；
- 为什么选它；
- 失败后尝试了什么、下一步是什么。

成本、延迟、权重、健康分等内部细节放在专家面板。默认用户不需要阅读评分公式，但必须能回答“谁做的、为什么是它、失败后发生了什么”。

路由事件需要有版本号、可重放输入摘要，以及能力矩阵和 Provider 可用性快照，便于区分策略、模型档案和健康状态变化。摘要与快照只包含脱敏的任务特征、模型档案和状态，不保存文件正文、密钥或完整本地路径。当前已实现规则层回放与快照差异报告；本地矩阵覆盖两个协议，真实 `--real` smoke 也支持显式 primary/fallback 两组配置，但真实 Provider 运行结果仍需单独接入故障矩阵。

桌面验收证据同时记录脱敏的 `surfaceJourney`（按步骤顺序去重的 `chat` / `work` / `codex`），使跨能力面执行可以被机器比较，而不依赖截图或原始任务文本。

路由质量现在有独立的确定性门禁：`pnpm --silent routing:gate -- --json` 回放 50 条主样例和 54 条独立 hold-out 样例，并检查规则路由硬能力底线、两个 Provider 配置场景下的 fallback 链覆盖。当前门槛是两套样例的规则路由准确率都至少 70%，智能路由首选满足硬能力且首选 Provider 故障后有合格接手模型；规则信号补强后当前结果为主样例 100%、hold-out 100%、硬能力 100%、接手覆盖 100%，严格标签准确率分别为 88% 和 90.7%。这些读数只证明分类器、能力矩阵和链路构造，不证明真实回答质量、真实 Provider 延迟或生产 SLA。

### P2：ChatGPT Desktop 能力基线

在可靠执行闭环通过后，再按下面顺序补齐基线功能：

1. 对话历史、搜索、项目上下文、记忆和自定义指令；
2. 文件上传、本地文件夹、文档/表格/演示成果和导出；
3. 联网搜索、引用和长任务进度；
4. 全局快捷键、系统托盘/菜单栏、窗口恢复和多窗口；
5. 语音输入输出、活动窗口上下文和多模态输入；
6. 自动更新、崩溃报告和跨平台安装体验。

每项功能必须挂到统一任务链上。例如文件上传不是 Work 专属入口，代码仓库也不是 Codex 专属会话；它们都应成为任务上下文或步骤能力。这样才能避免重新做出三个互相割裂的应用。

## 5. 不做的事情

在 M22 期间明确不做以下工作：

- 不增加 Chat / Work / Codex 三套独立会话状态。
- 不让用户手动维护复杂的模型路由规则作为默认体验。
- 不在真实 Provider 证据缺失时宣称“智能路由准确率”或“自动恢复 SLA”。
- 不在未解决跨平台构建和签名之前扩展大量系统级集成。
- 不为了追求 ChatGPT Desktop 功能数量而提前加入语音、插件市场或复杂多 Agent 编排。

这些功能不是永久取消，而是排在“任务链可信”之后。

## 6. 核心指标与门槛

### 可靠性

| 指标 | M22 门槛 | 证据 |
|---|---:|---|
| 流式五场景通过率 | 5/5 | Mac QA 包记录 |
| 账本崩溃窗口重复副作用 | 0 次 | 两个 fault point 的重启记录 |
| 用户取消后后台继续请求 | 0 次 | Provider 日志和进程日志 |
| 部分输出被静默拼接 | 0 次 | 截断/断流验收 |
| 真实 Provider 故障矩阵 | 8/8 场景有结果 | 脱敏报告 |

### 路由质量

| 指标 | 目标 |
|---|---:|
| 硬能力满足率 | ≥ 98% |
| 路由链最终可用率 | ≥ 95% |
| 路由事件可解释率（用户能指出实际模型与原因） | ≥ 90% |
| 手动锁定模型时不偷偷换模型 | 100% |

这些是发布前目标，不是当前已达成事实；当前已有的规则、回环和录制测试只能证明局部行为。

### 性能

先建立基线，再定公开承诺：

- 冷启动到可输入：p50 / p95；
- 提交到 headers：p50 / p95；
- headers 到首个正文 chunk：p50 / p95；
- 失败切换额外耗时；
- 空闲内存和流式任务峰值内存；
- CPU、电池和包体积。

主 chunk 已接近 600 kB，应在 P2 之前完成前端拆包；这是体验优化任务，不应与路由正确性混在同一批发布门禁里。

## 7. 四个团队的工作切分

### 产品

冻结“一个目标、一条任务链、三个能力面”的术语和对象模型。所有新功能先回答它属于任务上下文、步骤能力还是结果交付物，避免重新制造独立模式。

### 设计

把路由信息设计成渐进披露：默认一行，点击展开尝试链，专家模式再显示评分。失败态必须区分“已保留部分结果”“等待用户确认”“可以继续”“需要重新开始”。

### 工程

优先完成 ProviderAdapter 契约、跨 Provider 集成测试、Mac WebView 黄金路径和 Windows/Linux 原生构建。路由算法的每次变更都要带录制样例回放，不能只看单元测试。

### 安全

把本地文件访问、Provider 密钥、提示注入和工具副作用放进同一条威胁模型。重点验证：文件根目录逃逸、恶意文档指令、未知副作用重放、明文历史、日志中的路径和密钥片段。

## 8. 需要用户研究验证的关键问题

1. 用户是否理解“自动路由”而不是把它误解为又一个模型名称？
2. 用户看到降级链时，最需要的是原因、成本、预计等待时间还是控制按钮？
3. “继续执行”与“重新执行”是否能被清楚区分？
4. 目标跨越 Chat、Work、Codex 时，用户是否认为它仍是同一个任务？
5. 什么时候用户愿意手动锁定模型？锁定后是否期待能力不匹配提醒？
6. 本地文件和终端权限在默认、计划、完全访问三档之间是否足够清楚？

## 9. 结论

当前项目最合理的方向不是继续复制 ChatGPT Desktop 的表面功能，而是先把它变成一个“ChatGPT Desktop 能做的事 + 更可信的模型控制面”。具体执行顺序是：

```text
统一任务模型
  → Mac 真实桌面黄金路径
  → 真实 Provider 中立性
  → 路由透明度和可重放证据
  → Windows/Linux 构建、安装和签名
  → 再补齐语音、快捷唤起和更多桌面能力
```

完成 M22 后，项目才有资格从“有完整基础设施的 Alpha”进入“可邀请用户试用的 Beta”。
