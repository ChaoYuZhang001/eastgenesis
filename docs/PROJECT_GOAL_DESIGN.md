# 项目 / 目标 / 计划：竞品调研与设计

调研日期 2026-10-02。只用官方来源（官方文档、帮助中心、GitHub 仓库、论文），查不到就写「官方未提到」。

## 统一工作台产品边界（M11）

Chat、Work、Codex 合并为一个统一任务工作台里的三种**能力面**：Chat 负责对话与推理，Work 负责文件、研究、文档、表格和演示文稿，Codex 负责代码仓库、终端和本地开发。它们不再作为需要用户先选择的三个产品模式，而是由同一条任务路由根据输入、附件、工作目录和工具需求自动判断；用户也可以显式指定能力面，作为透明路由的可解释约束。

这一边界服务于四个核心原则：模型中立（能力面不绑定某一家模型）、路由透明（展示能力面、模型、理由和降级链）、失败可恢复（能力面与 Provider 解耦，失败后可继续尝试）和智能路由（按任务事实选择能力，而不是按产品标签分流）。同一个 Goal 可以在不同轮次和不同步骤进入不同能力面，避免把长任务锁死在初始模式。当前实现已把能力面接入 `Classification`、任务级和步骤级路由事件、Composer 预览、执行时间线、CLI、持久化 checkpoint、同任务恢复、工具能力/调用契约、内置文件适配器的恢复前副作用探测，以及迁移 6/7 的跨进程调用账本、恢复租约和执行心跳；下一步是做真实崩溃窗口验证、第三方适配器的探测/回滚语义，再做真实桌面外壳和多 Provider 失败切换验证。

## 0. 先说三个与需求描述不符的地方

调研前先核对事实，避免照着错的假设做设计。

1. **「长任务/目标」不是竞品标配。** 只有 ZCode 和 Codex 有「一句话目标 → 自动多轮 → 每轮校验 → 达成收尾」这一整套。Routa 是看板驱动的多智能体流转（人工推卡片），AIPOM 是人在环中的可编辑计划图，Manus 是会话内自主推进、没有独立目标对象，WorkBuddy 只有 Planning 状态、没有自动校验。所以「对齐竞品」在这里只对齐 ZCode/Codex 两家，其余是各自不同的设计。
2. **WorkBuddy 的项目层比描述里薄。** 官方只有 Workspaces（= 文件读写范围 + 权限判定边界），**没有**项目级指令、知识库、技能；它的 Memory 是账号级、跨 workspace 全局生效。所以「项目承载指令/连接器/技能」这条在官方文档里找不到依据。
3. **Manus 的继承有明确的时间差。** 官方写明：指令更新在**当前任务下次发消息时**生效；知识库文件更新**只对更新后新建的任务**生效，已有任务不受影响。这个传播规则值得照抄（见 2.4）。

另外两点值得注意：ZCode 的「上限」是**用量上限**，官方文档里没有轮次上限；Cowork 和 Codex 都明确把**沙箱（能访问什么）**和**审批（何时暂停）**当作两个独立控件——这和我们已有的权限三档 + 任务模式正交的设计一致。

## 2. EastGenesis 采用的设计

### 2.1 三层结构

```
项目 Project          顶层容器：指令、上下文文件夹、项目记忆、默认路由偏好
  └─ 目标 Goal        项目内的长任务单元：一句话目标 + 多轮推进 + 每轮校验
       └─ 任务 Task   执行单元（现有的一「轮」），属于某个目标；也可以不属于目标独立存在
```

任务可以不挂在目标下（现在的用法不变），目标也可以不挂在项目下（用默认项目）。三层都是可选的，不强制。

### 2.2 项目字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | |
| `name` | TEXT | |
| `description` | TEXT | 可为空 |
| `instructions` | TEXT | 项目级行为规则，注入每次任务的系统提示 |
| `context_folders` | TEXT(JSON) | 本地文件夹列表；只记路径，不复制内容 |
| `routing_preference` | TEXT | `economy` / `balanced` / `best`，复用现有 `Preference` |
| `created_at` / `updated_at` | INTEGER | |

记忆不放进项目表，而是在 `memories` 表加 `project_id`（NULL = 全局）。这样记忆的查询和现在完全一样，只是多一个过滤条件。

**继承规则**（照抄 Manus 的时间差语义）：

- `instructions`、`routing_preference`：**下一次任务**生效，已在跑的任务不受影响。
- `context_folders`：**只对新建的任务生效**，已在跑的任务保持原来注入的上下文。
- 原因：指令是提示词，改了就马上生效符合直觉；上下文文件夹涉及已经读进模型的内容，中途换掉会让同一轮任务的前后不一致。

### 2.3 目标机制

**设定方式**：输入框切到「目标模式」后直接输入，或用 `/goal <描述>`。

**推进循环**（复用现有 `AgentRuntime`，不新写执行器）：

```
设定目标
  → 跑一轮任务（现有的 plan → 执行 → 反思）
  → 校验：目标达成没有？（决策层 checkDone + evaluateResult）
  → 未达成 → 生成下一轮的目标（= 上一轮校验给出的「下一步动作」）→ 回到上一步
  → 达成 → 收尾
```

**校验的实据要求**（这是 ZCode 最值得抄的一条）。`checkDone` 现在只喂 `goal` 和 `result` 两段文本，模型很容易被一段听起来像结论的回复骗过去。改成喂三类实据，任一类能证明进展才算数：

1. 工具调用记录（现有 `tool_result` 事件里有 `ok` 和内容）
2. 文件变更（现有 `RunFile`，工具的写操作已经有记录）
3. 命令输出（`tool_result` 里 `run_command` 的内容）

判定改成三态：**已达成**（有实据且 `checkDone` 为真）、**未达成**（有实据但没做完）、**存疑**（没有任何实据）→ 存疑按未达成处理，但面板上标出来，让用户知道是「说不清」而不是「做完了」。

**停止条件**（三个，任一触发即停）：

- 校验判定达成
- 用户暂停 / 清除
- 达到用量上限（**用现有 `Budget` 的 `maxLlmCalls`，不新造轮次上限**，因为 ZCode 官方也只有用量上限）

**状态机**：

```
idle ──设定──> running ──校验通过──> completed
                │  ▲
             暂停│  │恢复
                ▼  │
              paused ──清除──> cleared
                │
              失败或超预算 ──> failed / budget_exceeded
```

一个会话同时只有一个目标（照抄 ZCode）。停止键 = 暂停，不是清除。

### 2.4 计划可视化

**按轮次分组的清单**，不做看板、不做可编辑 DAG。

理由：现有运行时的 `plan` 事件已经带 `revision` 和 `continuation` 两个字段，天然就是「轮」的概念，直接拿来分组，不需要新建数据模型。看板（Routa）适合人工推卡片的多智能体流水线，我们是单目标自动推进，用不上；可编辑 DAG（AIPOM）要用户手工维护图，复杂度高、收益低。

```
┌─ 目标：整理下载文件夹的 PDF，按主题分类 ────────┐
│  已用 4 分 12 秒 · 第 3 轮 · [暂停] [清除]        │
├──────────────────────────────────────────────────┤
│  第 1 轮  列出目录里的文件                        │
│    ✓ 列出 ~/Downloads 的 PDF（12 个）             │
│    ✓ 读取每个文件的前两页                         │
│  第 2 轮  判断主题                                │
│    ✓ 识别出 4 个主题                              │
│    ✓ 生成分类清单                                 │
│  第 3 轮  ▶ 移动文件（进行中）                    │
│    ✓ 建 4 个主题目录                              │
│    · 移动 12 个文件            ← 当前待办          │
└──────────────────────────────────────────────────┘
```

- 每轮标题 = 上一轮校验给出的「下一步动作」
- 清单项归属**首次出现**的那一轮，后续轮完成也留在原组（照抄 ZCode）
- 当前轮显示进度和待办
- 实据在清单项上可展开（哪次工具调用、改了哪些文件）

### 2.5 任务模式

输入框内三选一（与已有的权限三档并排，两者正交）：

| 模式 | 行为 | 与权限的关系 |
|---|---|---|
| **快速**（默认） | 现在的行为：判断是否走规划，直接执行 | 互不影响 |
| **计划** | 先出计划，用户确认后才执行 | 互不影响 |
| **目标** | 设定目标，自动多轮推进 | 每轮的工具调用照走权限闸门 |

**冲突规则**：计划模式与目标模式不能同时开（照抄 ZCode）。切到目标模式时自动退出计划模式，并在界面上说明原因。任务运行中不能切换模式，也不能设目标。

### 2.6 智能路由与三层的关系

路由仍是核心，三层只是给它提供**默认值**，不替代它。

**优先级**：任务级 > 目标级 > 项目级 > 全局默认（`balanced`）。

```
任务里手动锁定模型          ← 最高，现有的 route.lock 不变
任务级偏好（输入框临时选）
目标级偏好（goal.routing_preference）
项目级偏好（project.routing_preference）
全局默认 balanced
```

**路由决策本身不动**：每个 LLM 调用点仍由 `DecisionLayer.routeTask` 决定（Jev + 规则引擎 + 三级降级）。偏好只影响评分权重，不影响「由谁决策」。

**路由面板**：保留折叠在回答下方。新增一行「偏好来源：项目 X」，让用户知道当前用的偏好是哪一层给的。

### 测试口径

- `project.ts` / `goal.ts` 是纯函数，直接单测，不进 jsdom。
- 迁移 4 在 Rust 侧 `cargo test` 覆盖（照 `migrations` 现有测试）。
- 目标状态机：每个状态转换一条测试，非法转换要拒绝。
