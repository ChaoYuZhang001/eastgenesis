# Jev 真实 API 验证报告

日期 2026-10-02。环境：Linux VM（Node 22.23.2），`@typesafe-ai/sdk@0.6.0`，端点 `api.typesafe.ai`，模型 `jev-latest`。Key 来自 `.env.local`（600 权限，跑完已删除），报告和日志里没有 Key。

数据来源：第 1–3 节是当天用旧 Key 采的；第 4–6 节是新 Key 采的（含 54 条 hold-out 的真实采样）。所有数字都是真实调用，回放录制的回答不需要 Key，命令见末尾。

## 结论

| 项 | 结果 |
|---|---|
| choice 冒烟（3 用例 × 10 轮 = 30 次） | 30/30 调用成功，30/30 分类正确，置信度 0.920–1.000 |
| P50 < 300ms | **未达标**：328ms（新 Key 复测单轮 359ms）。VM 到服务端的裸往返 P50 250ms，加 Jev 自身约 70–100ms（估），本机网络下 300ms 基本不可达，以 Mac 复测为准 |
| 无 Key / 假 Key | 3/3 降级到 rules（第 3 级），不抛异常；假 Key 时服务端 401，本次会话内第 1 级被停用 |
| 50 条标注样例（训练集，2 轮采样） | 降级 8.0%，整条链 50/50（100.0%），两轮相同 |

| 过拟合判断 | hold-out（96.3%）比 50 条（100%）低 2 条，但**明显高于 90% 与目标 85%**，没有过拟合迹象；50 条的 100% 是调参集上的饱和值，写报告时以 hold-out 为准 |
| tool_use 问句 v2 | 采用。hold-out 上误报 13–14 → **0** 条，漏报 0 → 0，链准确率 83.3–85.2% → 96.3%，两轮一致 |

## 1. choice 冒烟（`tools/jev-smoke-test.mjs`）

首次运行，3 条逐条记录：

| 用例 | 期望 | 返回 | 置信度 | 耗时 |
|---|---|---|---|---|
| a "帮我写一个快速排序" | code | code | 1.000 | 815ms |
| b "解释一下量子纠缠" | reasoning | reasoning | 0.920 | 379ms |
| c "你好" | simple | simple | 1.000 | 299ms |

10 轮（30 次）：a 10/10 置信度 1.000；b 10/10 置信度 0.920–0.940；c 10/10 置信度 1.000。合计最小 283ms，**P50 328ms**，P90 393ms，最大 848ms；另两次独立采样 P50 为 317ms、340ms。新 Key 复测（3 次）：3/3 正确，P50 359ms。

**VM 网络基线**（Node `fetch` 打 `api.typesafe.ai`，不带 Key，服务端 404；1 次建连 + 24 次复用连接）：首次 1398ms（含 DNS、TCP、TLS）；复用连接后最小 238ms，**P50 250ms**，P90 320ms。curl 直连 TCP 握手 198–266ms。一次往返就占了 P50 的大半，Jev 自身约 70–100ms（估），与官方「70–500ms」一致。这部分是网络距离，代码里没有可压的；Mac 上跑 `node tools/jev-smoke-test.mjs 10` 才能判断目标是否达成。

## 2. 路由决策与降级链（`tools/jev-route-test.mjs`，旧措辞下的真实运行）

`routeTask` 用的是产品自己的能力问句（code / reasoning / tool_use），类型名与冒烟的三选一不同：「解释量子纠缠」在产品里是 qa。

| 提示 | 决策来源 | 置信度 | 耗时 | 降级链 |
|---|---|---|---|---|
| a 帮我写一个快速排序 | rules（第 3 级，已降级） | 0.600 | 979ms | cloud-jev ✗ 置信度 0.12 低于阈值 0.6 → local-jev ✗ 没有选择本地决策模型 → rules ✓ |

| c 你好 | cloud-jev（第 1 级） | 0.920 | 537ms | cloud-jev ✓ |

示例 a 当时被降级：Jev 给的概率是 code 0.97、reasoning 约 0.55、tool_use 0.04，旧置信度策略取全部最小，被 reasoning 拉到 0.08–0.12。新策略下它的置信度是 0.92（reasoning 不再计入），由 `tests/jev-backend.test.ts` 用这组真实概率钉住。

## 4. 置信度策略：只计入会改变结果的判断

官方 skill（`.claude/skills/typesafe-ai/`）和它指向的文档给出的结论：

- **一个请求问多个独立维度**：是官方推荐的 speculative fan-out，三问保留，不拆。问题已经是一项能力一个窄问题。「只问一个 Choice：这是什么类型」不采用：能力会同时成立，官方也说「几个标签可能同时成立时，每个标签一个 Noul」。
- **不设阈值、取最高概率**：答案取 ≥ 0.5 没变；阈值只用来决定要不要换备用系统。完全不设阈值（取最大）在 hold-out 上只有 74.1%，低于规则引擎单独的 81.5%。
- **置信度算法**：原来「全部取最小」把不影响结果的分支也算进去了（主类型已是 code 时的 reasoning 只影响软性加分），是过度降级的原因。现在只取会改变主类型或硬性能力的判断的最小 |2p−1|（`src/decision/classification.ts`）。Noul 本身没有 confidence，仍用 |2p−1| 表示它离 0.5 多远。
- 问题和阈值集中到 `src/decision/jev-config.ts`（官方建议，方便审阅）。

50 条训练集上的策略对照（2 轮采样，阈值 0.6）：

| 策略 | 交给规则引擎 | 其中 Jev 本来也对 | 留用的 Jev 里错的 | 整条链准确率 |
|---|---|---|---|---|
| 旧：全部取最小 | 58.0% | 66–72% | 9.5% | 96.0%（48/50） |
| **新：只算会改变结果的判断** | **8.0%** | — | — | **100.0%（50/50）** |
| 对照：取最大 | 0% | — | 20–24% | 76–80% |

## 5. hold-out：54 条独立盲写样例（真实采样）

样例由独立子代理按同一套标注规范盲写，写的时候没有看过规则引擎和 Jev 的问题。**只用来检验，不拿来调规则或问题措辞**。每轮 54 次真实调用，两轮独立采样。

| 措辞 | 轮次 | 降级比例 | Jev 上场率 | 整条链准确率 | 规则引擎单独 |
|---|---|---|---|---|---|
| v1（旧 tool_use 措辞） | 1 | 29.6% | 70.4% | 85.2%（46/54） | 81.5% |
| v1 | 2 | 29.6% | 70.4% | 83.3%（45/54） | 81.5% |
| **v2（现行）** | 1 | **11.1%** | **88.9%** | **96.3%（52/54）** | 81.5% |
| **v2（现行）** | 2 | **11.1%** | **88.9%** | **96.3%（52/54）** | 81.5% |

v2 下 Jev 单独 54/54，两轮都是 100%；也就是说这 54 条里 Jev 的分类本身全对，链上的 2 条错误全部来自降级后由规则引擎接手（`ho-code-en-02`、`ho-reasoning-en-02` 在 v1 时也是被降级的那两条）。

关于过拟合：关注的是 hold-out 会不会明显低于 50 条上的 90% 那一版策略。结果是 hold-out 在 v2 措辞下 96.3%，**高于** 50 条那版的 90%，也高于 85% 的验收目标。50 条上的 100% 要打折看：那一版措辞是在这 50 条上定下来的，属于调参集上的饱和值。真实准确性以 96.3%（54 条，95% 区间约 87–99%）为准。

剩下 2 条错误（两轮都一样）：

| 样例 | 期望 | Jev 概率（两轮） | Jev 判断 | 决定性置信度 | 结果 |
|---|---|---|---|---|---|
| ho-code-en-02 | code [code, reasoning] | code 0.96 / 0.95，reasoning 0.95 / 0.95，tool_use 0.30 / 0.29 | 对 | 0.40 / 0.42（由 tool_use 决定） | 低于 0.6，交给规则引擎，规则判错 |
| ho-reasoning-en-02 | reasoning | code 0.04 / 0.03，reasoning 0.78 / 0.73，tool_use 0.02 / 0.02 | 对 | 0.56 / 0.46（由 reasoning 决定） | 低于 0.6，交给规则引擎，规则判错 |

两条都是同一个原因：Jev 判对了，但会改变结果的那一问不够确定，按阈值交给了规则引擎，规则引擎判错。这和标签结构无关（2026-10-03 用 `evaluateChain` 回放核实，此前写成「能力标签粒度问题」是错的）。ho-code-en-02 的不确定来自 tool_use：「写个脚本数值验证」要不要真的运行，本身就模棱两可。把阈值降到 0.5 只能救回第 1 轮的 ho-reasoning-en-02，救不回另外三次，这正是第 7 节里 0.5 两轮 98.1% / 96.3% 的来源；为这两条再往下调阈值，会把真不确定的判断也交给 Jev，不做。

## 6. tool_use 问句措辞：v1 → v2

问题：v1 措辞把附件当成「要读本地文件」，对长文本/图片附件误报 tool_use（50 条上 4 例，概率 0.81–0.90）。v2 写明「附件已提供、读它不算动作」，同时保留「对附件本身改名、移动、保存、发送仍算动作」。

| 指标（hold-out，2 轮合计） | v1 | v2 |
|---|---|---|
| tool_use 误报 | 27 | **0** |
| tool_use 漏报 | 0 | 0 |
| tool_use 精确率 | 0.45 | **1.00** |
| 整条链准确率 | 83.3–85.2% | **96.3%** |
| 降级比例 | 29.6% | **11.1%** |

采用条件（先定后看，达成才采用）：误报下降、漏报不增、整条链准确率不降。三条都达成，且两轮一致，所以采用。code 与 reasoning 的精确率没变（0.89 / 0.75），没有引入新的误报。

## 7. 阈值：0.6 还是 0.7

| 阈值 | hold-out 链准确率（两轮） | hold-out 降级 / Jev 上场 | 50 条链准确率 | 50 条降级 / Jev 上场 |
|---|---|---|---|---|
| 0.5 | 96.3% / 98.1% | 3.7–7.4% / 92.6–96.3% | 100% | 6.0% / 94.0% |
| **0.6（现行）** | **96.3% / 96.3%** | **11.1% / 88.9%** | **100%** | **8.0% / 92.0%** |
| 0.7 | 94.4% / 94.4% | 13.0% / 87.0% | 100% | 12.0% / 88.0% |
| 0.8 | 92.6% | 18.5% / 81.5% | 100% | 20.0–22.0% / 78.0–80.0% |

建议留 0.6：hold-out 上准确率最高（96.3%），降级只有 11.1%。0.7 在 hold-out 上反而更低（94.4%），在 50 条上只多降 4% 却少 Jev 上场 4%。0.5 更激进，hold-out 两轮波动更大（96.3% / 98.1%）。若只想更保守，0.8 在 hold-out 上会掉到 92.6%。
